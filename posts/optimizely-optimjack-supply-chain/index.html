[보안이슈] Optimizely 가입 절차 결함으로 178개 조직 사이트에 악성 스크립트, 'OPTIMJACK' 공급망 공격

한 줄 요약

웹 A/B 테스트 서비스 Optimizely의 가입 절차 결함으로 공격자가 다른 고객의 프로젝트 JavaScript를 고칠 수 있었고, 2026년 11월 16일 업체의 정상 CDN을 통해 178개 조직 사이트 방문자에게 지갑 주소 바꿔치기·카드 정보 탈취 코드가 배포됐다.

무슨 일이 있었나

  • 2026-11-16: 공격자가 Optimizely Web Experimentation의 계정 가입 절차 결함을 악용했다. Optimizely 보안 권고에 따르면 이 결함으로 대상 고객 계정의 사용자를 사칭할 수 있었고, 공격자는 고객 프로젝트의 선택 항목인 “Project JavaScript”에 악성 코드를 넣었다.
  • 피해 범위: Unit 42 분석에 따르면 최소 178개 조직의 사이트가 변조된 Optimizely 스크립트를 방문자에게 내려보냈다. 보도에 따르면 CNN, BBC, Fox News, Zoom, Salesforce, GitLab 등 큰 사이트가 포함됐지만, Optimizely는 피해 고객 목록을 확인해 주지 않았다.
  • 업체 대응: Optimizely는 공격 당일 이를 탐지해 악성 코드 전달을 막고, 탐지 후 3시간 안에 취약점을 닫았으며, 영향받은 모든 프로젝트에서 주입 코드를 지웠다고 밝혔다. 또 이번 사고는 자격 증명 유출이 아니며, Web Experimentation 고객의 5% 미만이 영향을 받았고 다른 제품은 영향이 없다고 했다.
  • 미해결: 가입 절차 결함이 어떻게 남의 프로젝트 쓰기 권한까지 이어졌는지는 공개되지 않았다. 공격 주체를 자처한 그룹도 없다.

왜 문제가 되나

Optimizely 같은 실험 도구는 사이트 페이지 안에서 직접 실행되는 서드파티 스크립트다. 사이트 운영자가 자기 코드를 한 줄도 바꾸지 않았는데, 업체 쪽에서 내려보내는 스크립트가 바뀌면서 방문자 브라우저에 악성 코드가 실행됐다.

sequenceDiagram
    participant A as 공격자
    participant O as Optimizely (가입·프로젝트)
    participant CDN as Optimizely CDN
    participant S as 고객 사이트
    participant V as 방문자 브라우저
    A->>O: 가입 절차 결함으로 계정 생성
    A->>O: 다른 고객의 Project JavaScript 수정
    O->>CDN: 변조된 스크립트 배포
    V->>S: 사이트 접속
    S->>V: 페이지 + Optimizely 스크립트 로드 지시
    V->>CDN: 스크립트 요청 (정상 도메인)
    CDN-->>V: 악성 코드 포함 스크립트
    Note over V: 지갑 주소 바꿔치기, 결제 폼 카드 정보 수집

Unit 42 분석으로 확인된 악성 코드 동작은 다음과 같다.

  • 암호화폐 클리퍼: 방문자가 복사한 암호화폐 지갑 주소를 공격자의 주소로 바꿨다.
  • 웹 스키밍: 결제 폼에 입력한 카드 정보를 수집했다.
  • iOS 익스플로잇 킷 전달 시도: iPhone·iPad 방문자에게는 Coruna·DarkSword라는 iOS 익스플로잇 킷을 전달하려 했다(Unit 42 분석). 실제 기기가 감염됐는지는 확인되지 않았다.

왜 막기 어려웠나: 악성 스크립트가 Optimizely의 정상 CDN에서 정상 인증서로 내려왔기 때문에, 출처를 보는 CSP도 내용이 자주 바뀌는 파일에 쓰기 어려운 SRI도 제 역할을 하기 어려웠다. “믿는 업체”가 곧 공격 통로가 된 것이다. 자세한 내용은 아래 Q&A에 정리했다.

용어 정리

용어설명
소프트웨어 공급망 공격 (Software Supply Chain Attack)피해자를 직접 공격하지 않고, 피해자가 믿고 쓰는 외부 서비스·코드를 먼저 장악해 그 경로로 악성 코드를 퍼뜨리는 공격. 이번에는 웹사이트에 붙는 실험 도구가 통로였다.
A/B 테스트 (A/B Testing)방문자를 나눠 서로 다른 버전의 화면을 보여 주고 어느 쪽 반응이 좋은지 비교하는 실험 방법. 웹에서는 보통 외부 업체의 스크립트가 방문자 브라우저에서 페이지를 바꿔 실험을 돌린다.
서드파티 스크립트 (Third-party Script)웹사이트가 자기 서버가 아닌 외부 업체에서 불러와 실행하는 JavaScript. 분석·광고·실험 도구가 대표적이며, 사이트와 같은 권한으로 페이지를 읽고 바꿀 수 있다.
콘텐츠 전송 네트워크 (Content Delivery Network, CDN)파일을 전 세계 서버에 복제해 가까운 곳에서 빠르게 내려주는 서비스. 이번 악성 스크립트는 Optimizely의 정상 CDN에서 배포돼 겉보기에 정상 파일이었다.
아이프레임 (Inline Frame, iframe)웹 페이지 안에 다른 웹 페이지를 상자처럼 끼워 넣는 HTML 요소. 출처가 다르면 바깥 페이지의 스크립트가 상자 안 내용을 읽을 수 없어, 결제 입력란을 분리하는 데 쓴다.
동일 출처 정책 (Same-Origin Policy, SOP)브라우저가 출처(프로토콜·도메인·포트)가 다른 페이지끼리 서로의 내용을 읽지 못하게 막는 기본 규칙. 아이프레임 분리가 효과를 내는 근거다.
멀티테넌트 (Multi-tenant)하나의 서비스와 인프라를 여러 고객사(테넌트)가 함께 쓰는 구조. 각 고객의 데이터와 설정이 서로 보이거나 바뀌지 않게 격리하는 것이 핵심이다.
부적절한 접근 통제 (Broken Access Control)로그인 여부는 확인하지만 그 사용자가 해당 자원을 다룰 권한이 있는지는 제대로 확인하지 않는 결함. 남의 데이터를 보거나 고치는 사고로 이어진다.
암호화폐 클리퍼 (Crypto Clipper)화면·입력창·클립보드에 있는 암호화폐 지갑 주소를 공격자 주소로 몰래 바꿔, 송금이 공격자에게 가게 만드는 악성 코드.
웹 스키밍 (Web Skimming)결제 페이지에 심은 스크립트가 사용자가 입력한 카드 번호 등을 가로채 외부로 보내는 공격. 메이지카트(Magecart)형 공격이라고도 부른다.
하위 리소스 무결성 (Subresource Integrity, SRI)스크립트 태그에 파일의 해시값을 적어 두고, 브라우저가 받은 파일의 해시가 다르면 실행하지 않게 하는 기능. 내용이 자주 바뀌는 파일에는 쓰기 어렵다.
콘텐츠 보안 정책 (Content Security Policy, CSP)브라우저에게 이 페이지가 어디서 스크립트를 불러오고 어디로 데이터를 보낼 수 있는지 알려주는 보안 헤더. 허용한 업체가 뚫리면 막지 못하는 한계도 있다.

대응 방법

  • Optimizely 고객: Project JavaScript와 실험 코드는 고객 팀이 관리 화면에서 직접 작성하는 칸이므로, 우리 팀이 작성하지 않은 코드(악성으로 의심되는 코드)가 들어 있는지 검토한다. 침입 원인은 계정 탈취가 아니라 업체 쪽 결함이지만, 공격자가 남겨 두었을 수 있는 접근을 끊기 위해 Optimizely 계정의 API 토큰·협업자 목록을 점검하고 자격 증명을 교체한다.
  • 11월 16일 영향 페이지에서 카드를 입력한 사용자는 노출 가능성을 염두에 두고 카드사 이상 거래 알림을 확인한다.
  • 암호화폐 송금 시 붙여넣은 주소를 앞뒤 몇 글자만이 아니라 전체로 대조한다.
  • 사이트 운영자: 결제 페이지에는 꼭 필요한 서드파티 스크립트만 남기고, CSP의 connect-src로 외부 전송 대상을 좁히고, 이미지 요청(img-src)과 폼 전송(form-action)으로 빠져나가는 길도 함께 좁힌다. 스크립트 변경을 감시하는 도구(클라이언트 측 모니터링, CSP 위반 보고)를 둔다.

공부하며 생긴 질문들

Q. Optimizely는 무엇을 하는 회사이고, A/B 테스트 도구는 웹사이트에 어떻게 붙어서 동작할까?

A. Optimizely는 웹사이트 실험(A/B 테스트)과 개인화, 콘텐츠 관리 도구를 파는 미국의 디지털 경험 플랫폼 회사다. A/B 테스트는 방문자를 나눠 한쪽에는 원래 화면(A), 다른 쪽에는 버튼 색이나 문구를 바꾼 화면(B)을 보여 주고, 어느 쪽에서 가입·구매가 더 많이 일어나는지 비교하는 방법이다. 도입 방식이 이 사건의 핵심이다. 고객사는 자기 사이트 페이지에 Optimizely가 준 스크립트 태그 한 줄을 넣고, 그 스크립트는 고객 프로젝트별 JavaScript 파일을 Optimizely의 CDN에서 불러온다. 마케터가 Optimizely 관리 화면에서 실험을 만들면 그 내용이 이 파일에 반영되고, 방문자 브라우저에서 실행되면서 페이지를 직접 바꾼다. 역할을 나누면, 고객사는 무엇을 실험할지 정하고 바꿀 화면(변형)과 성과 지표를 만든다. 변형은 보통 시각 편집기로 만들고 필요하면 변형별 코드를 붙인다. Optimizely는 그 설정을 파일로 만들어 CDN으로 배포하고, 방문자를 일관되게 A·B 그룹에 나눠 해당 화면을 보여 주고, 클릭·구매 같은 이벤트를 모아 통계적으로 의미 있는 차이인지 계산해 준다. 이번에 악성 코드가 들어간 “Project JavaScript”는 특정 실험의 A·B 코드가 아니라, 프로젝트가 붙은 모든 페이지에서 실험보다 먼저 실행되는 공통 사용자 코드 칸이다. 그래서 여기에 코드가 들어가면 실험 대상 여부와 상관없이 모든 방문자에게 실행된다. 즉 고객사는 개발자를 거치지 않고 화면을 바꿀 수 있는 대신, Optimizely 쪽 프로젝트 파일에 들어간 코드가 그대로 자기 사이트에서 실행되는 구조를 받아들인 셈이다. 이번 공격자는 바로 이 프로젝트 파일을 고칠 수 있었고, 그래서 업체의 정상 CDN을 통해 178개 조직의 사이트에 악성 코드가 퍼졌다.

Q. 서드파티 스크립트는 사이트 안에서 어떤 권한을 가지고, 왜 결제 페이지에서 특히 위험할까? 아이프레임으로 분리하면 무엇이 달라지나?

A. 서드파티 스크립트는 사이트 운영자가 아닌 외부 업체 서버에서 불러오는 JavaScript다. 중요한 점은 파일이 어디서 왔는지보다 어디서 실행되는지다. 페이지에 <script> 태그로 불러온 순간 그 스크립트는 사이트 자기 코드와 똑같은 권한으로 돈다. 페이지 내용을 읽고 바꾸고, 사용자가 입력창에 치는 글자를 읽고, HttpOnly가 아닌 쿠키를 읽고, 외부로 요청을 보낼 수 있다. 그래서 결제 페이지에서 특히 위험하다. 사용자가 카드 번호를 입력하는 칸이 사이트 자체 폼이라면, 같은 페이지의 어떤 스크립트든 그 값을 읽어 밖으로 보낼 수 있다. 이번 공격의 카드 정보 수집도 사이트 자체 결제 폼을 노렸다.

아이프레임(iframe)은 페이지 안에 다른 페이지를 상자처럼 끼워 넣는 HTML 요소다. 브라우저의 동일 출처 정책 때문에, 상자 안 페이지의 출처(도메인)가 바깥과 다르면 바깥 페이지의 스크립트는 상자 안 내용을 읽을 수 없다. 많은 결제 대행사가 카드 입력란을 자기 도메인의 아이프레임으로 제공하는 이유다. 이렇게 하면 쇼핑몰 페이지에 붙은 서드파티 스크립트가 뚫려도 아이프레임 안에 입력된 카드 번호는 읽지 못한다. 다만 완벽하지는 않다. 바깥 페이지를 조작할 수 있는 악성 스크립트는 진짜 아이프레임을 숨기고 그 자리에 가짜 입력창을 그려 넣을 수 있으므로, 결제 페이지에는 꼭 필요한 서드파티 스크립트만 남기는 것이 함께 가야 한다. 결제 단계에서 아예 결제 대행사 페이지로 이동시키는 방식이면 쇼핑몰 쪽 스크립트가 결제 화면에 남지 않아 이런 위험이 더 줄어든다.

Q. CSP(Content Security Policy, 콘텐츠 보안 정책)는 무엇이고 어떻게 동작할까?

A. CSP는 웹 서버가 응답 헤더로 브라우저에게 “이 페이지는 이런 출처의 자원만 쓸 수 있다”고 알려 주는 허용 목록이다. 예를 들어 script-src 'self' cdn.optimizely.com이라고 보내면, 브라우저는 내 사이트와 Optimizely CDN에서 온 스크립트만 실행하고 그 밖의 주소에서 불러온 스크립트나 페이지 안에 끼워 넣은 인라인 스크립트는 막는다. 항목은 자원 종류별로 나뉜다. script-src는 스크립트를 불러올 곳, connect-src는 스크립트가 데이터를 보낼 수 있는 곳, img-src는 이미지를 불러올 곳, frame-src는 아이프레임으로 넣을 수 있는 곳이다. 그래서 CSP는 원래 XSS 피해를 줄이는 대표 수단이다. 공격자가 입력값으로 스크립트를 끼워 넣어도 인라인 스크립트나 허용 목록 밖의 스크립트는 실행되지 않고, 실행되더라도 데이터를 보낼 수 있는 곳이 제한된다. 막는 기준은 출처(어디서 왔나)이지 내용(무엇이 들었나)이 아니라는 점이 중요한데, 이 차이가 이번 사건에서 CSP가 막지 못한 이유로 이어진다.

Q. CSP와 SRI는 이런 공격을 얼마나 막을 수 있을까? 내용이 계속 바뀌는 실험·분석 스크립트에는 왜 SRI를 쓰기 어렵나?

A. SRI(Subresource Integrity, 하위 리소스 무결성)는 스크립트 태그에 그 파일의 해시값을 함께 적어 두는 기능이다. 브라우저는 파일을 받으면 해시를 계산해 적힌 값과 비교하고, 한 글자라도 다르면 실행하지 않는다. CSP가 출처를 확인한다면 SRI는 내용을 확인하는 셈이라, 이론상 이번처럼 허용된 업체의 파일이 바뀐 공격을 정확히 막는다. 문제는 Optimizely 같은 실험 도구의 프로젝트 파일은 마케터가 실험을 고칠 때마다 내용이 바뀐다는 점이다. 해시를 고정하면 정상적인 실험 변경도 모두 차단되므로 사실상 쓸 수 없다. SRI는 버전이 고정된 라이브러리처럼 내용이 바뀌지 않는 파일에 맞는 도구다. CSP는 이번 공격에서 스크립트 실행을 막지 못했다. 고객 사이트가 Optimizely 도메인을 이미 허용해 두었기 때문이다. 그래도 유출 단계는 좁힐 수 있다. connect-src는 스크립트가 fetch·XMLHttpRequest·웹소켓·sendBeacon으로 연결할 수 있는 주소를 정하고, 값을 이미지 주소에 붙여 요청하는 길은 img-src, 폼 전송은 form-action이 따로 맡는다. 이 세 항목을 모두 좁게 걸어 둔 사이트라면, 악성 코드가 실행돼도 카드 정보를 공격자 서버로 보내는 단계에서 막혔을 수 있다. connect-src만 막으면 나머지 길로 우회할 수 있다. 결국 두 기능 모두 “믿고 허용한 업체가 뚫린 경우”에는 한계가 있고, 결제 페이지처럼 민감한 곳에서는 서드파티 스크립트 자체를 줄이는 것이 가장 확실하다.

Q. “가입 절차 결함으로 남의 프로젝트를 고칠 수 있었다”는 건 어떤 종류의 권한 검증 실수일까? SaaS의 멀티테넌트 격리는 보통 어떻게 설계하나?

A. Optimizely는 가입 절차 결함이 어떻게 다른 고객 프로젝트의 쓰기 권한으로 이어졌는지 공개하지 않았다. 업체 보안 권고는 “이 결함으로 대상 고객 계정의 사용자를 사칭했다”는 정도다. 그래서 아래는 이런 사고를 만드는 흔한 유형이다. 큰 범주로는 부적절한 접근 통제(Broken Access Control)에 해당하며, OWASP Top 10에서 가장 흔한 웹 취약점으로 꼽히는 유형이다. 첫째는 인증과 인가를 혼동하는 경우다. 서버가 “로그인한 사용자인가”만 확인하고 “이 프로젝트가 이 사용자 소속인가”는 확인하지 않으면, 요청에 담긴 프로젝트 번호만 바꿔도 남의 프로젝트를 고칠 수 있다(IDOR). 둘째는 가입·초대 단계에서 소속이 잘못 정해지는 경우다. 가입할 때 들어갈 계정이나 조직을 사용자가 보낸 값으로 정하거나, 이메일 도메인만 보고 기존 조직에 넣어 주거나, 초대 확인을 건너뛸 수 있으면, 새로 만든 계정이 처음부터 다른 고객 조직의 일원이 된다. 이번 사건 설명은 두 번째 유형에 더 가까워 보이지만, 공식 원인 발표 전까지는 단정할 수 없다.

멀티테넌트 서비스는 보통 이렇게 격리한다. 고객 구분값(테넌트 ID)은 요청에 담긴 값이 아니라 서버가 로그인 세션에서 꺼낸 값만 믿는다. 모든 조회·수정 요청마다 “이 대상이 이 테넌트 소속이고, 이 사용자 역할로 이 동작이 허용되는가”를 서버에서 확인하고, 확인되지 않으면 기본으로 거부한다. 데이터베이스 쿼리에도 테넌트 조건이 빠지지 않게 공통 계층이나 행 단위 보안으로 강제한다. 조직 합류는 일회용 초대 링크와 이메일 확인을 거치게 하고, 프로젝트 코드처럼 고객 사이트에 바로 배포되는 변경은 감사 로그를 남겨 이상 변경을 빨리 찾을 수 있게 한다.

배운 점

  • 공격자는 Optimizely 가입 절차 결함으로 고객 계정 사용자를 사칭해 Project JavaScript에 악성 코드를 넣었고, 그 코드가 업체의 정상 CDN을 타고 178개 조직의 방문자 브라우저에서 실행됐다. XSS처럼 남의 사이트에서 공격자 스크립트가 돈다는 결과는 같지만, 입력값이 아니라 사이트가 믿고 불러온 외부 스크립트로 들어왔다는 점이 달랐다.
  • CSP는 “어디서 왔나”만 보고 SRI는 “무엇이 들었나”를 보지만, 허용한 업체가 뚫리고 내용이 계속 바뀌는 스크립트라면 둘 다 한계가 있다는 걸 알게 됐다. connect-src만 막으면 이미지 요청이나 폼 전송으로 우회할 수 있다는 것도 새로 배웠다.
  • 아이프레임은 동일 출처 정책으로 결제 입력란을 지켜 주지만, 가짜 입력창을 그려 넣는 공격까지 막지는 못한다. 결국 결제 페이지에서는 서드파티 스크립트 자체를 줄이는 게 가장 확실하다.
  • 내 블로그도 Mermaid, 검색 같은 기능을 외부 CDN(jsdelivr)에서 불러오고 있다. 나도 모르게 “믿고 불러오는 외부 스크립트”를 쓰고 있었다는 걸 알게 됐다.
  • 내 홈랩 SOC 대시보드 설정을 다시 보니 CSP로 스크립트 출처와 연결 대상을 내 사이트로 묶고, 쓰지 않는 폼 전송은 아예 막아 두었다. 방문자 로그를 화면에 보여 주는 페이지라 XSS를 정제로 놓쳤을 때의 2차 방어선이라는 걸 이제 이해했다.

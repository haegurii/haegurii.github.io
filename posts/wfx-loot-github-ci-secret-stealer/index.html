[보안이슈] 탈취한 GitHub 계정 4,837개로 CI 시크릿 탈취 코드 심은 'wfx-loot' 캠페인

한 줄 요약

정체불명의 공격자가 탈취한 GitHub 계정 4,837개로 61,764개 저장소에 무해해 보이는 PR을 열어 쓰기 권한을 떠본 뒤, 권한이 있는 저장소의 CI 워크플로에 시크릿 탈취 코드를 넣고 1분 안에 되돌려 흔적을 지웠다(Aikido 집계 최소 1,806개 저장소에서 실행).

무슨 일이 있었나

  • 2026-11-10 12:45 UTC ~ 11-11 15:00 UTC: 공격자가 탈취한 계정 4,837개로 61,764개 저장소에 wfx-docs 브랜치에서 docs: dependency audit notes라는 PR을 열었다. 이 PR은 마크다운 파일 하나만 추가하는 탐색용이었다.
  • 같은 기간: 쓰기 권한이 확인된 저장소에는 ci: refresh build cache 같은 평범한 이름의 커밋으로 기존 워크플로에 약 1,500줄을 덧붙였다. 새 워크플로를 임시 브랜치에 만들거나 npm postinstall 훅을 쓰는 방식도 있었다.
  • 실행 후: 1분 안에 변경을 되돌리고, 워크플로 실행 기록과 로그를 삭제했다.
  • 집계 차이: Aikido는 탈취 코드가 실제 실행된 저장소를 최소 1,806개(다른 요약에서는 1,835개)로, SafeDep은 악성 커밋이 발견된 저장소를 8,093개로 셌다. 세는 기준이 달라서 생긴 차이다.
  • 번진 범위: 자동 배포 설정 때문에 최소 Packagist 패키지 1개와 Go 모듈 1개에도 페이로드가 실렸다.
  • 4,837개 계정이 처음에 어떻게 탈취됐는지는 확인되지 않았다. Aikido는 훔친 GitHub 자격 증명과 토큰이 쓰였다고만 밝혔고, Endor Labs는 유출된 GitHub CLI OAuth 토큰으로 탐색 PR이 열렸다는 피해자 한 명의 진술을 전했다. 10월 GhostAction 캠페인 피해 계정이 이번에도 당한 경우가 많았고 100개 넘는 저장소에서는 GhostAction이 심어 둔 워크플로 파일에 이번 코드가 들어갔지만, Aikido는 인프라와 탈취 코드 설계가 달라 서로 다른 행위자일 가능성이 높다고 봤다.

왜 문제가 되나 (공격 원리)

CI 러너는 배포를 위해 클라우드 키, 패키지 배포 토큰 같은 강한 시크릿을 갖고 돈다. 워크플로 파일을 고칠 수 있으면 그 시크릿을 꺼내는 단계를 하나 끼워 넣을 수 있다. 즉 “저장소 쓰기 권한 = CI 시크릿 접근 권한”에 가깝다.

sequenceDiagram
    participant A as 공격자
    participant R as 피해 저장소
    participant CI as Actions 러너
    participant S as 공격자 서버
    A->>R: 탈취 토큰으로 탐색 PR (문서 파일 1개)
    R-->>A: 쓰기 권한 여부 확인
    A->>R: "ci: refresh build cache" 커밋으로 워크플로 수정
    R->>CI: 워크플로 자동 실행
    CI->>CI: 시크릿, GITHUB_TOKEN, OIDC 토큰, 자격 증명 파일 수집
    CI->>S: HTTP로 유출
    A->>R: 1분 안에 커밋 되돌림, 실행 기록 삭제

이 공격이 배울 만한 이유는 세 가지다.

  1. 취약점 없이 정상 권한만으로 이뤄졌다. 계정·토큰 하나가 새면 그 사람이 쓸 수 있는 모든 저장소가 위험해진다.
  2. 흔적 지우기가 정교하다. 그래서 공격자 커밋 직후 Actions 탭에서 실행 번호가 하나 비어 있는 것이 거의 유일한 흔적인 경우가 많다.
  3. CI 신뢰가 클라우드로 이어진다. OIDC 신뢰 설정이 넓으면, 탈취한 짧은 토큰으로 AWS·Azure 역할까지 얻을 수 있다. 실제로 이 탈취 코드는 클라우드 신뢰 설정도 노렸다.

용어 정리

용어설명
지속적 통합/지속적 배포 (Continuous Integration/Continuous Delivery, CI/CD)코드를 올리면 빌드·테스트·배포가 자동으로 돌아가는 파이프라인. 배포에 필요한 클라우드 키 같은 시크릿을 들고 있어 공격 가치가 높다.
워크플로 (Workflow)GitHub Actions에서 언제(이벤트), 어디서(러너), 무엇을(작업 단계) 실행할지 적은 YAML 파일. 저장소의 .github/workflows/ 폴더에 두며, 이 파일을 고칠 수 있으면 CI에서 실행될 코드를 정할 수 있다.
러너 (Runner)워크플로의 작업을 실제로 실행하는 서버. GitHub가 작업마다 새로 띄워 주는 것과 조직이 직접 운영하는 것(셀프 호스티드)이 있으며, 실행 중에는 시크릿이 이 서버에 들어온다.
GitHub Actions 시크릿 (GitHub Actions Secrets)워크플로가 실행될 때 환경 변수로 주입되는 암호화된 비밀 값. 워크플로 파일을 고칠 수 있는 사람은 사실상 이 값을 꺼낼 수 있다.
OIDC 페더레이션 (OpenID Connect Federation)CI 작업이 장기 키 대신 짧게 유효한 토큰으로 클라우드에 로그인하는 방식. 클라우드 쪽 신뢰 설정이 넓으면 탈취한 토큰으로 클라우드 역할을 얻을 수 있다.
소프트웨어 공급망 공격 (Software Supply Chain Attack)최종 대상을 직접 치지 않고, 그 대상이 쓰는 코드·패키지·빌드 과정을 오염시켜 피해를 퍼뜨리는 공격.
개인 액세스 토큰 (Personal Access Token, PAT)비밀번호 대신 API·Git 작업에 쓰는 GitHub 토큰. 유출되면 2단계 인증을 거치지 않고 그 권한만큼 저장소를 조작할 수 있다.

대응 방법

  • 흔적 찾기: 내가 쓰기 권한을 가진 저장소에서 wfx-docs 브랜치, docs: dependency audit notes PR, ci: refresh build cache 커밋을 검색한다. 탐색 PR만 있었어도 그 PR을 연 계정은 탈취된 것으로 본다.
  • 실행 여부 판단: 공격자 커밋 직후 Actions 실행 번호에 빈칸이 있는지 확인한다.
  • 실행됐다면: 그 워크플로가 닿을 수 있었던 모든 시크릿, 클라우드 역할, 배포 토큰을 탈취된 것으로 보고 교체한다. AWS·Azure에 새로 생긴 신뢰 관계·자격 증명도 점검한다.
  • 예방: PAT는 범위와 기한을 최소로, 가능하면 fine-grained 토큰을 쓴다. 기본 브랜치 보호·필수 리뷰, .github/workflows/ 변경에 CODEOWNERS 리뷰를 건다. GITHUB_TOKEN 기본 권한은 읽기 전용으로 둔다. OIDC 신뢰 조건은 저장소·브랜치·환경까지 좁힌다. 배포용 시크릿은 저장소 시크릿 대신 배포 환경(Environment) 시크릿으로 옮기고, 특정 브랜치에서만 쓰이거나 지정한 사람이 승인해야 풀리도록 보호 규칙을 건다. 그러면 임시 브랜치나 덧붙인 단계에서는 그 시크릿을 꺼낼 수 없다.

공부하며 생긴 질문들

Q. GitHub Actions 워크플로는 무엇을 위해 쓰고, 어떻게 동작할까?

A. GitHub Actions는 저장소에서 어떤 일이 일어나면 정해 둔 작업을 자동으로 실행해 주는 GitHub의 CI/CD 서비스다. 그 “언제, 어디서, 무엇을”을 적은 설정 파일이 워크플로이고, 저장소의 .github/workflows/ 폴더에 YAML로 둔다. 워크플로는 세 부분으로 읽으면 된다. on은 실행 계기(push, PR 생성, 정해진 시각 등), runs-on은 작업을 돌릴 서버(러너), jobs/steps는 차례로 실행할 명령이다. 예를 들어 이 블로그의 배포 워크플로는 “main에 push되면(on) → GitHub가 띄운 우분투 서버에서(runs-on) → 코드를 받고, Ruby를 설치하고, Jekyll로 사이트를 빌드하고, 링크를 검사한 뒤, GitHub Pages에 배포한다(steps)”는 내용이다.

실무에서는 주로 이렇게 쓴다. PR이 올라오면 테스트·린트·보안 스캔을 돌려 실패하면 병합을 막고(CI), main에 병합되면 빌드해서 클라우드나 서버에 배포하고(CD), 태그를 달면 패키지를 만들어 npm 같은 저장소에 올리고, 매일 밤 의존성 취약점 검사를 돌린다. 배포와 패키지 게시를 하려면 클라우드 키·배포 토큰·npm 토큰 같은 시크릿이 필요하고, 이 값들은 워크플로가 실행되는 동안 러너에 들어온다. 그래서 워크플로 파일을 고칠 수 있는 사람은 러너에서 무엇이 실행될지를 정할 수 있고, 이것이 wfx-loot 공격자가 노린 지점이다.

Q. 워크플로 파일을 고칠 수 있는 사람은 왜 사실상 모든 Actions 시크릿을 읽을 수 있을까? 로그에서 시크릿이 ***로 가려지는데도 유출이 되는 이유는?

A. 먼저 시크릿은 특정 워크플로 파일에 묶여 있지 않다. 저장소·조직 단위로 등록한 시크릿은 그 저장소의 어떤 워크플로든 이름만 적으면 꺼내 쓸 수 있고, 워크플로 안에서 시크릿 전체를 한꺼번에 꺼내는 표현도 있다. 게다가 push로 실행되는 워크플로는 기본 브랜치에 있는 원본이 아니라 방금 push한 커밋 속의 워크플로 파일을 기준으로 돈다. 그래서 쓰기 권한이 있으면 기존 워크플로에 단계를 덧붙이거나 임시 브랜치에 새 워크플로를 만드는 것만으로, 리뷰를 거치지 않고 시크릿이 들어 있는 러너에서 원하는 코드를 실행할 수 있다. wfx-loot가 먼저 탐색 PR로 쓰기 권한부터 확인한 것도 이 때문이다. 외부 사람이 포크에서 보낸 PR로 도는 워크플로에는 기본적으로 시크릿이 전달되지 않기 때문에, 쓰기 권한이 곧 시크릿에 닿는 열쇠가 된다.

로그의 *** 가림은 접근 통제가 아니라 출력 필터다. GitHub는 실행 로그에 시크릿 값과 똑같은 문자열이 찍히면 그 부분만 ***로 바꿔 보여 줄 뿐, 실행 중인 코드가 시크릿을 읽는 것은 막지 않는다. 그래서 값을 로그에 찍지 않고 네트워크로 외부 서버에 바로 보내면 가림은 아무 소용이 없고, 값을 인코딩하거나 쪼개서 원래 문자열과 달라지게 해도 가려지지 않는다. wfx-loot도 로그가 아니라 HTTP로 공격자 서버에 보냈고, 끝나면 실행 기록까지 지웠다. 이 구조를 줄이는 방법은 아래 배포 환경·브랜치 보호 Q&A와 대응 방법에 정리했다.

Q. 공격자는 구체적으로 어떤 경로로 러너에서 코드를 실행시키고 시크릿을 가져갔을까?

A. 보도된 방식은 세 가지다. 가장 많이 쓴 것은 ci: refresh build cache 같은 평범한 이름의 커밋으로 기존 워크플로에 약 1,500줄을 덧붙이는 방식이고, 이 밖에 임시 브랜치에 새 워크플로를 만드는 방식과 npm postinstall 훅을 쓰는 방식이 있었다. postinstall은 패키지를 설치할 때 자동으로 실행되는 스크립트라, 워크플로 파일을 건드리지 않아도 CI가 npm install을 하는 순간 코드가 돈다. 어느 경로든 결과는 같다. 덧붙인 코드가 러너 안에서 시크릿, GITHUB_TOKEN, OIDC 토큰, 러너에 있던 자격 증명 파일을 모아 HTTP로 공격자 서버에 보냈다. 그다음 1분 안에 변경을 되돌리고 워크플로 실행 기록과 로그를 지워, 저장소만 보면 아무 일도 없었던 것처럼 만들었다.

Q. 공격자가 바로 악성 커밋을 넣지 않고 무해한 탐색 PR부터 연 이유는 무엇일까?

A. 가장 큰 이유는 쓰기 권한이 있는지 확인하는 것이다. 탐색 PR은 대상 저장소에 wfx-docs 브랜치를 직접 올려서 열었는데, 저장소에 브랜치를 올릴 수 있다는 것 자체가 쓰기 권한이 있다는 뜻이다. 앞에서 본 것처럼 외부 포크의 PR로 도는 워크플로에는 시크릿이 전달되지 않으므로, 공격자에게 필요한 것은 “이 계정으로 이 저장소에 직접 커밋할 수 있는가”였다. 여기에 몇 가지 이점이 더해진다. 첫째, 마크다운 파일 하나만 추가하는 문서 PR이라 악성 코드가 없어 보안 도구나 관리자의 눈에 덜 띈다. 둘째, 계정 4,837개와 저장소 6만여 개를 상대로 하므로, 먼저 가볍게 떠본 뒤 실제로 권한이 있는 곳(최소 1,800여 개)에만 탈취 코드를 넣으면 코드가 노출되는 횟수를 줄여 발각 위험이 낮아진다. 셋째, 훔친 토큰이 아직 살아 있는지도 함께 확인된다. 거꾸로 말하면, 동료 계정으로 뜬금없는 문서 PR이 올라오면 그 계정이 탈취됐다는 신호로 봐야 한다.

Q. 워크플로의 permissions에 적는 contents: read, pages: write, id-token: write는 무슨 뜻일까?

A. 워크플로가 실행될 때마다 GitHub는 그 실행 전용 토큰인 GITHUB_TOKEN을 자동으로 만들어 러너에 넣어 준다. permissions는 이 토큰이 무엇을 할 수 있는지 항목별로 정하는 곳이다. 저장소 주인이나 협업자 같은 사람의 권한과는 별개로, 워크플로라는 자동 실행 프로그램이 쓰는 토큰의 권한이다. contents: read는 저장소 코드를 읽기만 할 수 있다는 뜻으로, 코드를 받아 빌드하는 데 필요하고 커밋을 올리거나 고칠 수는 없다. pages: write는 GitHub Pages에 사이트를 배포할 수 있다는 뜻이다. id-token: write는 이 실행이 OIDC 신분증 토큰을 발급받을 수 있다는 뜻으로, Pages 배포도 이 토큰으로 “이 저장소의 main에서 돈 실행”임을 증명한다. 여기에 적지 않은 항목은 권한이 없다. 예를 들어 이 블로그의 배포 워크플로는 이 세 가지만 주기 때문에, 그 실행 중 토큰이 새도 코드를 바꾸거나 이슈·PR을 조작할 수는 없다. 다만 pages: write가 있어 사이트 배포는 가능하므로, 워크플로를 고칠 수 있는 사람은 사이트 내용을 바꿀 수 있다. wfx-loot가 GITHUB_TOKEN까지 훔친 이유도 여기에 있다. 권한을 넓게 준 저장소라면 훔친 토큰으로 코드에 직접 커밋할 수도 있기 때문에, 기본 권한은 읽기 전용으로 두고 필요한 항목만 워크플로에 적는 것이 좋다.

Q. OIDC 페더레이션은 장기 키를 없애려고 쓰는데, 이번처럼 CI가 장악되면 어떤 설정이 피해 범위를 줄여 주거나 키워 줄까?

A. OIDC를 쓰는 이유는 오래 살아 있는 클라우드 키를 시크릿에 넣어 두지 않기 위해서다. 예전에는 AWS 접근 키 같은 장기 키를 Actions 시크릿에 저장해 두고 배포했는데, 이 키는 지우기 전까지 계속 유효해서 한 번 새면 언제든 쓸 수 있다. OIDC 방식에서는 워크플로가 실행될 때마다 GitHub가 “이 토큰은 어느 저장소의, 어느 브랜치·환경에서 돈 워크플로가 받았다”는 정보가 담긴 짧은 신분증 토큰을 서명해 발급한다. 클라우드는 이 토큰이 GitHub가 발급한 것이 맞는지, 그리고 미리 정해 둔 신뢰 조건(저장소·브랜치·환경)에 맞는지 확인한 뒤, 보통 한 시간 안팎만 유효한 임시 자격 증명을 내준다. 저장할 장기 키가 아예 없는 것이 핵심이다.

CI가 장악되면 공격자 코드도 러너 안에서 이 토큰을 요청해 클라우드 자격 증명으로 바꿀 수 있으므로, OIDC 자체가 공격을 막아 주지는 않는다. 피해 크기는 설정에 달려 있다. 줄여 주는 설정은 신뢰 조건을 특정 저장소의 특정 브랜치나 승인이 필요한 배포 환경으로 좁히는 것이다. 그러면 공격자가 임시 브랜치나 덧붙인 단계에서 받은 토큰은 조건에 맞지 않아 거부된다. 역할 권한을 배포에 필요한 만큼만 주고, 자격 증명 유효 시간을 짧게 두는 것도 피해를 줄인다. 키우는 설정은 신뢰 조건이 넓은 경우다. 조직 안의 모든 저장소나 모든 브랜치를 믿도록 와일드카드를 쓰거나, 발급자만 확인하고 저장소 조건을 빠뜨리면, 장악한 아무 저장소에서나 그 클라우드 역할을 얻을 수 있다. 역할에 관리자급 권한이 붙어 있으면 짧은 시간 안에 새 사용자·키나 신뢰 관계를 만들어 두고 나갈 수 있어서, 임시 자격 증명이 만료돼도 접근이 남는다. wfx-loot의 탈취 코드가 클라우드 신뢰 설정까지 노린 것도 이 때문이다.

Q. 배포 환경 승인·브랜치 조건·브랜치 보호는 어떻게 동작하고, main에 바로 push하거나 관리자가 설정을 끌 수 있다면 어떤 상황에서 도움이 될까?

A. 이 설정들은 워크플로 실행 자체를 막지 않는다. 다른 브랜치에서도 워크플로는 돌 수 있고, 제한되는 것은 배포 환경(Environment)에 묶인 시크릿과 배포 단계다. 예를 들어 production 환경에 “main 브랜치에서만”이라는 조건을 걸면 임시 브랜치에서 돈 작업은 그 환경의 시크릿을 받지 못하고, 승인자를 지정하면 main에서 돈 작업도 승인 전까지 멈춘다. OIDC 신뢰 조건도 이 환경 이름으로 묶으면 클라우드 자격 증명까지 같은 문을 지나야 한다. main에 바로 push할 수 있으면 브랜치 조건은 통과되므로, main에 브랜치 보호를 걸어 PR과 리뷰 없이는 병합되지 않게 하고, 환경 승인에는 “실행을 일으킨 본인은 승인할 수 없음” 옵션을 켜서 층을 겹친다.

이 설정은 저장소 관리자가 끌 수 있으므로 관리자 계정 전체가 넘어가면 소용이 없다. 그래도 실제 침해는 권한이 일부만 있는 자격 증명이 새는 경우가 훨씬 많다. 쓰기 권한만 가진 협업자나 봇 계정, 관리 권한이 없는 토큰, 실행 중 받은 GITHUB_TOKEN은 코드를 올릴 수는 있어도 보호 설정을 끌 수는 없다. wfx-loot 피해 저장소 대부분은 시크릿이 저장소 단위로 등록돼 있어 쓰기 권한만으로 충분했지만, 이런 설정이 있었다면 main에 덧붙이는 커밋은 막히고 임시 브랜치에서는 배포 환경 시크릿이 풀리지 않았을 것이다. 다만 그 실행의 GITHUB_TOKEN과 저장소 단위로 남은 시크릿은 여전히 가져갈 수 있으므로, 배포용 시크릿을 배포 환경 단위로 옮기는 것이 함께 가야 한다. 혼자 운영하는 저장소라면 평소 쓰는 토큰을 관리(Administration) 권한이 없는 fine-grained 토큰으로 만들고 설정 변경은 2단계 인증을 거친 웹 화면에서만 하면, 토큰이 새도 보호 설정은 그대로 남는다. 정리하면 바닥은 계정 보안이고, 이 설정들은 관리자 계정이 아닌 무언가가 샜을 때 피해가 배포와 시크릿까지 번지지 않게 하는 장치다.

배운 점

  • 흐름은 계정·토큰 탈취 → 탐색 PR로 쓰기 권한 확인 → 권한이 있는 저장소에만 워크플로를 바꿔 러너의 시크릿을 HTTP로 빼돌리기 → 1분 안에 되돌리고 기록 지우기였다. 취약점 하나 없이 정상 권한만으로 이뤄졌다는 점이 가장 무서웠다.
  • OIDC도 혼자서는 막지 못한다. 임시 키라 털려도 덜 아프게 할 뿐이고, 배포 환경 승인과 브랜치 조건을 같이 걸어야 “아무 브랜치에서나 시크릿이 나오는” 구조를 끊을 수 있다.
  • 내 블로그 배포 워크플로를 점검해 보니 워크플로가 저장된 시크릿을 쓰지 않고 OIDC로 배포하고 있었다. 다만 시크릿이 없어도 배포 권한 자체가 지켜야 할 자산이라는 걸 알게 됐고, 배포 권한 보호를 점검할 거리로 남겼다.
  • 결국 가장 기본인 저장소 접근 권한을 잘 관리하는 게 답이라는 생각이 든다. 그걸 모르는 사람은 없을 텐데도 계정 4,837개가 뚫렸다는 걸 보면, 보안은 아는 것보다 지키는 게 더 어려운 것 같다.

한 줄 요약

Azure API Management(APIM) Classic 티어(Developer·Basic·Standard·Premium)의 결함이 실제 공격에 쓰여 게이트웨이에 저장된 API 키·OAuth/OIDC 클라이언트 시크릿·관리 토큰이 털렸고, 수정(11월 19일) 전에 빠져나간 비밀값은 여전히 유효할 수 있어 교체가 필요하다.

왜 문제가 되나

API 게이트웨이는 외부 요청을 받아 내부 백엔드로 넘겨주는 관문이다. 회사가 API를 여러 개 운영하면, 각 API가 인증·호출량 제한·기록 같은 공통 기능을 따로따로 만들어야 하고 외부에는 백엔드 주소가 여러 개 드러난다. 게이트웨이를 앞에 두면 이 일을 한곳에서 처리할 수 있다. 외부에는 게이트웨이 주소 하나만 보이고, 고객 인증(구독 키 확인), 한 고객이 너무 많이 호출하지 못하게 막는 제한, 요청 기록과 통계를 게이트웨이가 맡으며, 백엔드는 자기 업무에만 집중하면 된다. 내부 구조를 바꿔도 외부 주소는 그대로라 고객에게 영향이 없다는 장점도 있다. Azure API Management(APIM)는 이런 게이트웨이를 Microsoft가 관리형 서비스로 제공하는 것이다.

문제는 이 편리함의 대가다. 게이트웨이가 고객 대신 백엔드에 접속하려면, 백엔드에 들어갈 열쇠(백엔드 자격 증명, OAuth 클라이언트 시크릿, 연결 문자열)를 게이트웨이가 쥐고 있어야 한다. 공통 기능을 한곳에 모은 만큼 열쇠도 한곳에 모인다. 그래서 게이트웨이 한 곳이 뚫리면 뒤쪽 시스템 여러 곳의 열쇠가 한꺼번에 나간다.

Microsoft 안내에 따르면 노출 위험이 컸던 경우는 두 가지다.

  1. 권장 네트워크 보안 구성(가상 네트워크 연동 등)을 적용하지 않은 Classic 인스턴스
  2. 시크릿을 Azure Key Vault에 두지 않고 APIM 안(Named Values, 정책 본문)에 직접 넣어 둔 경우

여기서 핵심은 패치로는 끝나지 않는다는 점이다. 서비스 결함은 Microsoft가 고쳤지만 이미 복사된 비밀값은 그대로 유효하다. 또 APIM 안의 값만 새로 바꿔 넣으면 옛 값은 발급한 쪽(백엔드, ID 공급자)에서 여전히 살아 있다. 옛 값을 발급처에서 폐기해야 비로소 막힌다.

용어 정리

용어설명
API 게이트웨이 (API Gateway)여러 백엔드 API 앞에 서서 인증·호출 제한·라우팅을 대신 처리하는 관문. 백엔드에 접속할 자격 증명을 보관하는 경우가 많아, 뚫리면 뒤쪽 시스템 열쇠가 한꺼번에 샌다.
시크릿 (Secret)API 키, 클라이언트 시크릿, 연결 문자열, 토큰처럼 시스템에 접근하는 데 쓰는 비밀값. 이번 건은 APIM 안에 평문처럼 저장된 시크릿이 표적이었다.
키 볼트 (Key Vault)시크릿·암호 키·인증서를 따로 모아 접근 통제와 감사 기록을 붙여 보관하는 클라우드 서비스. Azure Key Vault를 참조하도록 설정한 경우 노출 범위가 줄었다고 안내됐다.
관리 ID (Managed Identity)Azure가 서비스에 붙여 주는 신분으로, 비밀값을 저장하지 않고도 다른 Azure 서비스에 로그인할 수 있게 한다. 짧게 유효한 토큰을 그때그때 받아 쓰기 때문에 훔쳐 갈 장기 비밀값이 남지 않는다.
가상 네트워크 (Virtual Network, VNet)클라우드 안에 만드는 사설 네트워크. 서비스를 여기에 넣으면 인터넷에서 바로 닿지 않게 하고, 허용한 경로로만 접근하게 할 수 있다.
인증 우회 (Authentication Bypass)정상적인 인증 절차를 거치지 않고 권한이 필요한 기능에 접근하는 취약점 유형. 이번 건의 근본 원인으로 일부 보도가 지목했지만 Microsoft가 확인하지는 않았다.
제로데이 (Zero-day)제조사가 수정본을 내기 전에 공격에 먼저 쓰인 취약점. 노르웨이 쪽에서 먼저 공격을 발견했고 수정은 그 뒤에 배포됐다.
시크릿 교체 (Secret Rotation)노출됐을 수 있는 비밀값을 새 값으로 바꾸고 옛 값을 폐기하는 조치. 저장 위치에서 값만 바꾸면 안 되고, 그 값을 발급한 시스템에서 옛 값을 무효로 해야 한다.

대응 방법

  • APIM 인스턴스 티어를 확인한다(Classic의 Developer·Basic·Standard·Premium이 대상).
  • 런타임 버전이 NSM이 안내한 수정 버전 이상인지 확인한다.
  • 구독 키, Named Values에 든 시크릿, 백엔드 자격 증명, OAuth/OIDC 클라이언트 시크릿, 연결 문자열, 정책에 적힌 자격 증명, 관리 API 토큰을 발급처에서 새로 만들고 옛 값을 폐기한다.
  • 시크릿은 APIM에 직접 넣지 말고 Key Vault 참조로 바꾼다. 관리 ID(Managed Identity)로 바꿀 수 있는 연결은 바꾼다.
  • 백엔드·ID 공급자 로그에서 11월 19일 전후로 낯선 출처의 호출, 평소와 다른 토큰 사용이 있었는지 찾는다.
  • 장기적으로 v2 티어 이전과 권장 네트워크 구성 적용을 검토한다.

공부하며 생긴 질문들

Q. API 게이트웨이는 왜 백엔드 시크릿을 저장해야 하나? Key Vault 참조나 관리 ID를 쓰면 이번 같은 사고에서 무엇이 달라지나?

A. 게이트웨이는 고객 대신 백엔드에 접속하기 때문에, 백엔드가 요구하는 열쇠를 어딘가에 갖고 있어야 한다. APIM에서는 이런 값을 Named Values라는 설정 칸에 넣어 두고 정책에서 꺼내 쓰는데, 값을 넣는 방식이 세 가지다. 평범한 값, APIM 안에 암호화해 보관하는 비밀 값, 그리고 Key Vault 참조다. Key Vault는 Azure의 비밀값 전용 금고 서비스다. 비밀값·암호 키·인증서를 한곳에 모아 두고, 누가 꺼낼 수 있는지 권한으로 통제하며, 꺼낸 기록을 남기고, 버전별로 교체할 수 있게 해 준다. Key Vault 참조를 쓰면 APIM에는 값 자체가 아니라 “금고의 몇 번 칸”이라는 주소만 남고, APIM은 필요할 때 자기 관리 ID로 금고에서 값을 받아 온다. 그래서 이번처럼 APIM에 저장된 설정을 읽어 가는 공격이라면, APIM 안에 직접 넣은 값은 그대로 털리지만 Key Vault 참조는 주소만 나가 노출 범위가 줄어든다. Microsoft가 노출 위험이 컸던 경우로 “시크릿을 Key Vault에 두지 않고 APIM 안에 직접 넣어 둔 경우”를 꼽은 이유다. 관리 ID는 한 걸음 더 나간다. 백엔드가 Azure 서비스라면 비밀값을 아예 저장하지 않고, APIM이 자기 신분으로 짧게 유효한 토큰을 받아 접속하게 할 수 있다. 훔쳐 갈 장기 비밀값이 처음부터 없는 셈이라, wfx-loot에서 본 OIDC와 같은 생각이다. 다만 APIM은 실행 중에 금고에서 받은 값을 쓸 수밖에 없으므로, NSM은 Key Vault를 썼더라도 모든 시크릿을 교체하라고 권했다.

Q. 노출 위험이 컸다는 “권장 네트워크 보안 구성을 적용하지 않은 인스턴스”는 어떤 모습이고, 권장 구성은 무엇일까?

A. Microsoft는 노출이 “문서화된 보안 모범 사례대로 구성하지 않은 Classic 인스턴스”에 한정됐다고만 밝혔고, 어떤 설정이 결정적이었는지는 공개하지 않았다. 그래서 아래는 Microsoft 문서가 권하는 일반적인 구성이다. 가장 흔한 “적용하지 않은” 모습은 만들 때 기본값 그대로 쓰는 인스턴스다. 게이트웨이와 관리용 주소가 모두 인터넷에 공개돼 있고, 누구나 그 주소에 요청을 보낼 수 있다. 권장 구성은 이 노출을 줄이는 방향이다. APIM을 가상 네트워크(VNet)에 넣어 내부 주소로만 닿게 하거나, 사설 엔드포인트로 연결하고, 네트워크 보안 그룹으로 허용할 출발지를 정한다. 인터넷에 열어야 하는 게이트웨이는 그 앞에 웹 방화벽이 있는 Application Gateway나 Front Door를 두고, 관리용 경로는 외부에 열지 않는다. 다만 Classic 티어에서는 가상 네트워크 연동을 Developer와 Premium에서만 쓸 수 있어, Basic·Standard 인스턴스는 구조적으로 공개 주소를 쓸 수밖에 없었다. 또 Classic 인스턴스마다 있던 구형 직접 관리 API는 Microsoft가 2025년 3월 지원을 끝냈는데, 일부 분석은 이 구형 관리 경로가 이번 공격 경로였을 것으로 보지만 Microsoft는 확인하지 않았다.

Q. 클라우드 서비스 측 결함은 왜 CVE 없이 서비스 공지로만 안내되는 경우가 많나? 고객은 이런 공지를 어디서 받아 보나?

A. CVE는 원래 “고객이 자기 컴퓨터에 설치한 소프트웨어의 결함”을 가리키는 번호로 쓰였다. 고객이 그 번호를 보고 해당 버전을 찾아 패치를 설치해야 했기 때문이다. 클라우드 서비스는 다르다. 프로그램이 업체 서버에서 돌고 수정도 업체가 한 번에 배포하므로, 고객이 설치할 패치가 없다. 그래서 업체들은 오랫동안 “고객이 할 일이 없으니 번호를 붙일 필요가 없다”고 보고, 영향받은 고객에게만 서비스 공지를 보내는 쪽을 택했다. 문제는 이번처럼 수정은 업체가 끝냈어도 고객이 할 일(시크릿 교체)이 남는 경우다. 번호가 없으면 취약점 관리 도구나 위협 정보 피드에 잡히지 않고, 공지를 못 본 조직은 대응이 늦어진다. Microsoft도 2024년부터는 고객이 할 일이 없더라도 심각한 클라우드 취약점에 CVE를 붙이겠다고 밝혔는데, 이번 건에는 아직 CVE가 없어 그 방침과 다르다는 지적이 나왔다. 고객이 공지를 받는 곳은 보통 세 군데다. 첫째, Azure Service Health 같은 클라우드 콘솔 안의 서비스 상태 알림이다. 영향받은 구독에만 보이므로, 알림 규칙을 걸어 메일·메신저로 받게 해 두지 않으면 포털에 들어가 봐야 알 수 있다. 둘째, 업체의 보안 공지와 기술 블로그다. 이번에도 Microsoft는 교체 가이드를 기술 블로그에 공개했다. 셋째, 국가 보안 기관의 권고다. 이번 건은 노르웨이 NSM 권고가 가장 자세한 공개 자료였다.

Q. “시크릿 교체”를 할 때 저장 위치에서 값을 바꾸는 것과 발급처에서 폐기하는 것은 어떻게 다르고, 교체 순서는 어떻게 잡아야 서비스가 끊기지 않나?

A. 저장 위치에서 바꾸는 것은 APIM(또는 Key Vault)에 들어 있는 값을 새 값으로 갈아 끼우는 일이고, 발급처에서 폐기하는 것은 그 값을 만들어 준 시스템(백엔드, ID 공급자, 결제 대행사 등)에서 옛 값을 더는 받지 않게 무효로 만드는 일이다. 노출된 값이 문제인 이유는 공격자가 이미 복사해 갔기 때문이다. 그래서 APIM 안의 값만 바꾸면 우리 게이트웨이는 새 값을 쓰지만, 공격자가 가진 옛 값은 발급처에서 여전히 통한다. 발급처에서 옛 값을 폐기해야 비로소 공격자의 열쇠가 쓸모없어진다. 구독 키처럼 APIM이 직접 발급하는 값은 APIM이 곧 발급처라 APIM에서 재발급하면 된다.

서비스가 끊기지 않으려면 새 값과 옛 값이 잠깐 함께 통하는 구간을 두고 순서를 지킨다. ① 발급처에서 새 값을 추가로 발급한다(옛 값은 아직 살려 둔다). ② 저장 위치에 새 값을 넣고, Key Vault 참조라면 APIM이 새 버전을 다시 읽게 한다. ③ 실제 호출이 새 값으로 정상 동작하는지 로그로 확인한다. ④ 발급처에서 옛 값을 폐기한다. ⑤ 이후 옛 값으로 들어오는 시도가 있는지 지켜본다. 이 시도가 있다면 그것이 바로 탈취된 값을 쓰는 공격자다. 기본·보조 키 두 개를 주는 서비스라면 한쪽으로 옮겨 놓고 다른 쪽을 재발급한 뒤 다시 옮기는 식으로 같은 효과를 낸다. 다만 이번처럼 실제로 탈취된 상황에서는 겹치는 구간을 최대한 짧게 잡아야 하고, 이미 악용 정황이 보이면 잠깐 서비스가 끊기더라도 옛 값부터 폐기하는 편이 낫다.

배운 점

  • API 게이트웨이는 인증·제한·기록을 한곳에 모아 편리한 만큼 뒤쪽 시스템의 열쇠도 한곳에 모인다. 후가쿠의 SSH 키, wfx-loot의 CI 시크릿에 이어 “열쇠가 모인 곳이 표적이 된다”는 같은 교훈을 클라우드에서 다시 봤다.
  • 비밀값은 APIM 안에 직접 넣기보다 Key Vault에 두고, 가능하면 관리 ID로 비밀 자체를 없애는 게 가장 좋다는 걸 알게 됐다. 꺼내 쓰는 비밀은 결국 어딘가에 잠깐 노출된다.
  • 업체가 패치를 끝내도 이미 복사된 키는 그대로 살아 있다. 저장 위치에서 값만 바꾸지 말고 발급처에서 옛 값을 폐기해야 비로소 끝난다.
  • 클라우드 결함은 CVE 없이 콘솔 안의 공지로만 오기도 한다. 클라우드를 쓴다면 공지를 기다리지 말고 알림을 받을 길부터 열어 둬야겠다.
